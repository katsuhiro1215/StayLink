# StayLink

小さな民宿向けの予約台帳。Go言語の学習用に、標準ライブラリを中心に作る試験的なプロジェクトです。

- 学習用です。宿泊者名簿など法令への適合は保証しません（業態により義務がある可能性があります。根拠法・項目は要確認）。
- サンプルデータはすべて架空です。
- 本番公開は想定していません。

## 構成

Go（標準 `net/http`・`html/template`）、PostgreSQL 18（Docker Compose）、DBドライバは `pgx`（`database/sql` 経由）。

## 動かし方

必要なもの：Go 1.27 以上、Docker（Docker Compose）。

```bash
# 1. 設定ファイルを作る（値は学習用のローカル専用）
cp .env.example .env

# 2. データベースを起動する（healthy になるまで待つ）
docker compose up -d --wait

# 3. テーブルを作る（未適用の migrations/*.sql だけ適用。何度実行してもよい）
scripts/migrate.sh

# 4. .env を読み込んで起動する
set -a; . ./.env; set +a
go run .
```

ブラウザで http://localhost:8090/ を開きます。ポートは環境変数 `PORT` で変えられます。

- 待ち受けは、自分のPCだけが接続できる `127.0.0.1` が既定です（`HOST` で変更可）。ログイン機能がないため、`HOST=0.0.0.0` でLANへ公開するのは、認証を付けるまで避けてください。
- 他のサイトのページからのPOSTは、標準の `CrossOriginProtection` で拒否します。ただし `curl` などヘッダのない送信は通すので、認証の代わりにはなりません。
- `scripts/migrate.sh` は排他していないので、同時に2つ実行しないでください。SQLファイルの中に `BEGIN` / `COMMIT` は書かないでください（スクリプトが1ファイル1トランザクションで包みます）。

止めるとき：アプリは `Ctrl+C`、データベースは `docker compose down`（データは残ります。消すときは `docker compose down -v`）。

## テスト

```bash
go test ./...                       # DBなしで動くテストだけ（DBが要るテストは自動で飛ばす）

scripts/test-db.sh                  # 初回だけ：テスト専用DB（staylink_test）を作って、テーブルを用意する
set -a; . ./.env; set +a
go test ./...                       # DBのテストも実行
STAYLINK_REQUIRE_DB=1 go test ./... # DBが使えないときは、飛ばさずに失敗させる（飛ばしたまま緑になるのを防ぐ）
```

- 以前から `.env` を使っている場合は、`.env.example` にある `TEST_DATABASE_URL` の行を `.env` にも足してください。足し忘れると、DBのテストが黙って飛ばされます（`STAYLINK_REQUIRE_DB=1` を付けると気づけます）。
- DBのテストは、**実際にコミットする**専用DBで動き、テストの前後で全テーブルを空にします（同時実行や、コミット後の見え方を確かめるため）。
- 開発用DBを空にしてしまわないよう、`TEST_DATABASE_URL` のDB名が `_test` で終わらない場合は、テストを中止します。
- 新しいマイグレーションを足したら、`scripts/migrate.sh`（開発用）と `scripts/test-db.sh`（テスト用）の両方を実行してください。
- このPCにはCコンパイラがなく、`go test -race`（データ競合の検出）は使えません。

## 今日の到着・出発（トップ）

- トップ（`/`）に、今日の**到着**（チェックイン日が今日）、**出発**（チェックアウト日が今日）、**滞在中**（昨日以前に到着し、明日以降に出発）を出します。取り消した予約は出ません。
- トップが予約を読むようになったため、DBに接続できないときは、トップも「エラー」の画面になります（以前のトップはDBを使いませんでした）。
- 同じ部屋で、前の方の出発と次の方の到着が同じ日でも、両方に出ます。
- 「今日」は、日本時間の今日の日付です（時刻は見ません）。分ける処理（`buildToday`）は、DBにも画面にも依存しない関数で、境界を表形式のテストで確かめています。

## 月間カレンダー

- `/calendar` が、行が部屋・列が日付の表を出します。月は `?month=2026-11` で指定でき、画面の「前の月」「次の月」「今月に戻る」でも切り替えられます。`?month=` が空のときは、警告なしで今月を表示します（正しくない値のときは、警告つきで今月）。
- **1マスが1泊**です。予約は、チェックイン日のマスから、チェックアウト日の**前日**のマスまでの横棒で、棒を選ぶと編集の画面へ進みます。チェックアウト日のマスは空いているので、同じ日に次の方がチェックインする様子が、そのまま見えます。
- 前の月から続く予約・次の月へ続く予約は、棒の端が点線になります。取り消した予約は出ません。
- 停止中の部屋は、その月に予約がある場合だけ出します（過去の記録を見られるように）。
- 表の組み立て（`buildCalendar`）は、DBにも画面にも依存しない関数にして、月またぎ・隣接・月の最初と最後の日などを、表形式のテストで確かめています。

## 管理者の作成（ログインの準備。画面からのログインは、次の段階で入ります）

- 登録画面は作りません。管理者は、コマンドで1人ずつ作ります。パスワードは**標準入力から1行**で渡します（コマンドの引数に出ないので、`ps` では見えません）。
- パスワードを画面に出さず、シェルの履歴にも残さない渡し方（端末で、パスワードを入力してEnterを押す）：

```bash
set -a; . ./.env; set +a
read -rsp 'パスワード: ' PW; echo
printf '%s\n' "$PW" | go run ./cmd/adduser -username admin
unset PW
```

- `printf '%s\n' 'パスワード' | go run ./cmd/adduser ...` のように直接打つと、パスワードがシェルの履歴に残ります。
- 標準入力を端末のまま（`go run ./cmd/adduser -username admin` だけ）にすると、入力が画面に表示されます。
- ユーザー名は、英小文字・数字・`.`・`_`・`-` の3〜32文字（英大文字は小文字に揃えます。全角などは使えません）。パスワードは10〜128文字（文字数で数えます）。
- パスワードは、入力された文字のまま扱います（NFCなどの正規化はしません）。入力方式によって、同じ見た目でも別のパスワードになりえます。
- パスワードは、標準ライブラリの PBKDF2-HMAC-SHA256（60万回、ソルト16バイト）でハッシュにして保存します。回数はハッシュの中に持つので、後で増やしても、古いハッシュを検証できます。
- 限界：argon2id・bcrypt（`golang.org/x/crypto` が要る）より、GPUでの総当たりには弱いです。60万回は、OWASPの目安（最新かは未確認）です。
- `migrations/004` を適用するため、新しい作業の前に `scripts/migrate.sh` と `scripts/test-db.sh` を実行してください。

## セキュリティ

- ハンドラが返す応答（404・405・500・静的ファイルを含む）に、`Content-Security-Policy`（自分のサイトのCSSだけを許可。スクリプト・インラインのスタイル・外部読み込みは不可。フォームの送信先も自分のサイトだけ）、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Cross-Origin-Opener-Policy: same-origin` を付けます（`net/http` がハンドラより前に返す、不正な要求への400などは対象外）。宿泊者名・連絡先を含む画面（`/static/` 以外）には、`Cache-Control: no-store` も付けて、戻る・進むでの再表示や履歴に残りにくくします。
- テンプレートとCSSが、この方針を守っているか（`<script>`・`style=`・`onclick=`・外部の参照がないか）を、テストで確かめています。破ると画面が崩れるためです。JavaScriptを足すときは、`internal/web/security.go` に `script-src self` を足してください。
- `Strict-Transport-Security` は付けていません（HTTPSを使わない前提。HTTPSで公開するなら、前に置くサーバー側で付けます）。
- **ログインがない**ため、`HOST=0.0.0.0` でLANへ公開しないでください。他のサイトからのPOSTを拒否するしくみ（`CrossOriginProtection`）は、認証の代わりにはなりません。
- ブラウザ（Playwright の Chromium、2026-11-06）で、カレンダー画面のCSS適用と、部屋の登録フォームの送信（303で一覧へ戻る）が、CSPに止められず、コンソールエラーが出ないことを確認しました。他のブラウザ・古いブラウザは未確認です。
- 保存に失敗して500の画面になったとき、入力した内容は残りません（再入力が必要です）。

## 未検証・できていないこと

- `go test -race`（データ競合の検出）：このPCにCコンパイラがなく、実行していません。
- 権限の低いDBユーザーでの `CREATE EXTENSION btree_gist`：管理者権限でだけ確認しています。
- 排他制約のGiST索引の性能：件数を増やした検証はしていません。
- 実機のスクリーンリーダー：読み上げの確認はしていません（空きマスのリンクは、読み上げから外しています）。
- 色のコントラスト比：計算していません（週末・今日の背景の差は小さめです）。
- デッドロックのやり直し：測定（70回以上の並行実行で失敗なし）に基づく設計で、PostgreSQLの公式な保証ではありません。

## 二重予約の防止のしくみ

- `migrations/003` が、`btree_gist` 拡張と排他制約 `reservations_no_overlap` を追加します。「同じ部屋」かつ「`daterange(check_in, check_out)` が重なる」予約の組を、DB自身が禁止します。
- 宿泊期間は、チェックイン日を含み、**チェックアウト日を含みません**。前の人のチェックアウト日に、次の人がチェックインできます。
- **取り消した予約は対象外**です。取り消せば、その期間はまた予約できます。
- アプリで「空いているか調べてから登録」しないのは、同時に2人が登録したときに、両方が通ってしまうためです。制約なら、同時でも必ず一方だけが成功します。
- 排他制約は、同時に入る別々の予約が互いを待ち合って、デッドロックになることがあります。その場合は、PostgreSQLが片方を中断するので、アプリが1文をやり直します（最大8回。待ち時間にはばらつきを入れます）。それでも尽きたときは、500ではなく「同時に他の操作があり、保存できませんでした。もう一度、ボタンを押してください」と案内します（入力は残ります）。
  - デッドロックの検出には、PostgreSQLの設定（`deadlock_timeout`、既定1秒）の時間がかかるので、混み合うと数秒待つことがあります。
  - やり直しは、1文ごとに自動でコミットされる使い方だけで安全です。そのため、予約の保存先（`reservation.Store`）は `*sql.DB` 専用で、トランザクションは受け取りません。
- 「どの予約と重なったか」の案内は、断られた**後**の別の問い合わせです。その間に取り消されるなどして、断った時点の状態と一致しないことがあります（その場合は詳細なしの案内になります）。
- 段階3までに、期間が重なった予約が開発DBに入っていると、`scripts/migrate.sh` は003で止まり、重なった予約のID（先頭の5組）を示します。どちらかを取り消すか期間を直してから、もう一度実行してください。
- `btree_gist` 拡張は、データベースごとに入れます（マイグレーションが入れます）。このプロジェクトのDBユーザーは管理者権限です。権限の低いユーザーで動かす場合は、事前に拡張を入れておく必要があるかもしれません（未確認）。
- 予約の表には、排他制約が持つ索引とは別に、`(room_id, check_in)` の索引（`migrations/002`）も残しています。月間カレンダーの範囲検索や、日付順の一覧で使うためです。
